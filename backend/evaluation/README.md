# Vision evaluation

Run this outside the production API. Evaluation does not save observations to PostgreSQL and does not create tasks.

Use `cases.example.json` as a format reference. Make your own `cases.json` with **human-reviewed** images and labels. The example label `0.85` is illustrative, not verified ground truth. Only label conditions you can directly see. A category absent from `expected` means **not visibly assessable**, not zero. Label an empty but visible sink as `dish_load: 0.0`.

Keep actual photos in a local ignored directory, not Git. Review every image and label before scoring. The initial set should balance kitchens, laundry, plants, lawns, irrelevant photos, and hard lighting/occlusion cases. Avoid using model output to assign ground truth.

From `backend`:

```powershell
python -m evaluation.run_vision --manifest evaluation/cases.json --images evaluation/images --output evaluation/report.json
```

The invocation makes one paid Nebius inference request per labeled image. Start with a few images and check credits. Results, including potentially sensitive visible evidence, are stored in the local JSON output. Keep this file out of Git.

The report contains category precision/recall, false positives and omissions, matched-category mean absolute severity error and tolerance agreement, and review rate. **Severity metrics only cover correctly detected categories**, so always read them alongside omission counts. Results are descriptive for this small dataset and do not prove calibrated confidence or generalization.

To rescore saved predictions without API calls, create a JSON mapping each case ID to the corresponding `VisionExtraction` object:

```powershell
python -m evaluation.run_vision --manifest evaluation/cases.json --images evaluation/images --predictions evaluation/predictions.json --output evaluation/report.json
```

A report generated by this tool also contains a `predictions` object which can be extracted for subsequent offline scoring. It is not accepted directly as a `--predictions` argument.

## Handling failed inference

Run the CLI as a module from `backend`:

```powershell
python -m evaluation.run_vision --manifest evaluation/cases.json --images evaluation/images --output evaluation/report_calibrated.json
```

The evaluator continues after individual image read, validation, or provider failures.
It writes a `failed` row with a sanitized exception **class**, not potentially
sensitive provider error text. It saves only successful predictions; failed
images have no synthetic zero-valued prediction. The report's
`failed_case_count`, `completed_case_count`, and `completion_rate` must be read
alongside detection precision/recall and severity metrics, which are calculated
**only from completed cases**. If every case fails, accuracy metrics are null.
The original images are not copied into the report. A failure still consumes
any inference request already sent to Nebius.

`--predictions` accepts either a mapping from case IDs to predictions or an
existing evaluator report containing a `predictions` mapping. Missing or invalid
saved predictions are recorded as failures without making Nebius requests.

## Initial measured kitchen benchmark

Five synthetic kitchen images were labeled with provisional human dishwashing workload values from 0 to 1. The first full run reported 5/5 category true positives, zero false positives/negatives, MAE 0.33, and 40% within tolerance. The revised rubric run completed only 4/5: conditional MAE 0.2025, 80% completion, one unexpected plant-condition candidate, and a nonzero score for a visually empty sink. Do not compare the two MAEs as if measured on identical completed cases. These are development-set results. Preserve both reports locally.

## Read-only scene inventory

```powershell
python -m evaluation.run_scene --image evaluation/images/kitchen_light_01_small.jpg --location kitchen --output evaluation/scene_light.json
```

The command calls Nebius but does not write household data. Its initial successful live response returned only one drain for a kitchen with multiple visible objects. The inventory is structurally validated but not completeness-calibrated. See `../../docs/scene-inventory.md`.
